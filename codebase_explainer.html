How modded-nanogpt works, from torchrun to validation loss

This repository is not a small teaching GPT. It is a highly optimized distributed training system built to train a language model as fast as possible on 8 H100s. The core script, train_gpt.py, handles launch, data loading, custom model logic, FlashAttention-3, bigram/value embeddings, a hybrid NorMuon+Adam optimizer, and Triton fused kernels.

Execution model
8-way distributed training
Hot path

Speed layer
Triton kernels + FP8 + FlashAttention-3

End-to-end pipeline

The codebase behaves like a staged training pipeline. Each colored block below corresponds to one major subsystem.

01

Launch

torchrun starts 8 worker processes and runs train_gpt.py on every rank.

02

Distributed setup

Ranks, world size, gradient accumulation, CUDA device, and process groups are initialized.

03

Load token shards

FineWeb token shards are read from binary files and packed into BOS-aligned variable-length batches.

04

Embed inputs

Token embeddings, bigram hash embeddings, and value embeddings are prepared before the transformer stack.

05

Attention / MLP stack

Custom attention, YaRN rotary logic, paired heads, gated value injection, and fused ReLU² MLP layers run.

06

Compute loss

Training uses a fused soft-capped cross-entropy path; evaluation computes logits explicitly.

07

Backward + optimizer

Gradients are reduced, sparsified where possible, then stepped with NorMuon and Adam.

08

Schedule updates

LR, momentum, attention windows, sequence length, batch size, and tied/untied embeddings evolve over time.

09

Validate & log

Validation loss is periodically computed and timing is tracked as the benchmark metric.

1) Launch & distributed setup

The training process starts very simply, but immediately turns into a distributed CUDA program.

What happens here

run.sh launches 8 local processes with torchrun. Then train_gpt.py reads environment variables like RANK, WORLD_SIZE, and LOCAL_RANK to initialize CUDA and distributed communications.

  • Ensures the world size divides 8
  • Sets grad_accum_steps = 8 // world_size
  • Initializes NCCL/Gloo process groups
  • Marks rank 0 as the logging / checkpointing process
run.sh entrypoint 
torchrun --standalone --nproc_per_node=8 train_gpt.py
train_gpt.py#L43-L58 distributed bootstrap 
rank = int(os.environ["RANK"])
world_size = int(os.environ["WORLD_SIZE"])
assert 8 % world_size == 0, "world_size must be a divisor of 8"
grad_accum_steps = 8 // world_size
grad_scale = 1 / grad_accum_steps
assert torch.cuda.is_available()
device = torch.device("cuda", int(os.environ["LOCAL_RANK"]))
torch.cuda.set_device(device)
dist.init_process_group(backend="cuda:nccl,cpu:gloo", device_id=device)
dist.barrier()
master_process = (rank == 0)
One shell command fans out into multiple synchronized GPU workers. The rest of the script assumes a distributed world from the beginning.

2) Data pipeline

The loader is specialized for benchmark throughput: binary token shards, BOS-aligned packing, async shard loading, and bigram hash generation.

What the loader does

  • Reads tokenized FineWeb shards from .bin files
  • Optionally aligns sequences to BOS boundaries
  • Packs many documents into one variable-length stream
  • Builds cum_lengths for varlen FlashAttention
  • Computes a bigram hash tensor for the bigram embedding path
  • Transfers everything to GPU with non_blocking=True
train_gpt.py#L1455-L1548 data generator

    num_tokens = num_tokens // grad_accum_steps

train_gpt.py#L1438-L1454 bigram hash 
def get_bigram_hash(x):
    rand_int_1 = 36313
    rand_int_2 = 27191
    mod = args.bigram_vocab_size-1
    x = x.to(torch.int32)
    out = torch.empty_like(x, pin_memory=True)
    out.copy_(x)
    out[0] = mod
    out[1:] = torch.bitwise_xor(rand_int_1 * out[1:], rand_int_2 * out[:-1]) % mod
This repo does not use a plain tutorial dataloader. It packs token streams specifically for efficient long-context varlen attention.

3) Model structure

The model is a customized GPT with extra embedding paths, gated residual behavior, parameter banks, and nonstandard layer topology.

Key model ideas

  • embed and lm_head start tied
  • bigram_embed injects adjacent-token information
  • value_embeds add another learned token-conditioned path
  • Attention and MLP weights live in large parameter banks instead of many independent modules
  • Some layers use paired-head attention
  • Layer 6 skips attention and reuses a skip connection
  • Backout subtracts part of an earlier state near the end

The forward pass is best understood as a main residual stream plus several side channels: bigram embeddings, value embeddings, skip gating, and backout behavior.

4) Attention path

Attention is not stock PyTorch attention. It is a specialized path that combines QK norm, rotary embeddings, optional paired heads, value embedding injection, and FlashAttention-3 varlen kernels.

What makes this attention special

  • Weights are passed in from parameter banks
  • norm(q) and norm(k) are applied before attention
  • YaRN rotary logic handles changing window sizes
  • Some layers use paired-head attention
  • Value embeddings can be injected through learned gates
  • Actual attention compute is delegated to flash_attn_varlen_func

Packed docs are treated as one long tensor, and cum_lengths tells the attention kernel where each sequence begins and ends.

5) Optimizer & schedule

The optimizer is hybrid and policy-driven: large projection matrices use NorMuon, while embeddings/gates/scalars use Adam. The training schedule also changes batch size, window sizes, and sequence length over time.

Optimizer mental model

TrainingManager is the orchestration layer. It decides which parameters belong to which optimizer, which communication mode they use, and when schedule changes should affect the model and data loader.

  • NorMuon for large parameter banks: qk_bank, vo_bank, mlp_bank
  • Adam for embeddings, gates, lambdas, and scalars
  • Some params are replicated, some sharded, and bigram gradients can be sharded_sparse
  • Adam only steps on odd steps
  • Embedding can split from lm_head later in training

def step_optimizers(self, step):
    step_lr = training_schedule.get_lr(step)
    muon_momentum = get_muon_momentum(step)
    do_adam = self._is_adam_step(step)

    for param, p_cfg in self.optimizer.param_cfgs.items():
        p_cfg.lr = p_cfg.initial_lr * step_lr
        if p_cfg.optim == "normuon":
            p_cfg.momentum = muon_momentum

    self.optimizer.step(do_adam=do_adam)
The optimizer is not just Adam with fancy hyperparameters. It is a split system with different update math and communication policies per parameter family.
Schedule changes matter a lot here: batch size, max sequence length, sliding attention windows, learning rate, Muon momentum, and embed untie timing all affect the live training behavior.

6) Training loop

The script first warms up and compiles representative kernels, resets the model state, then enters the measured train/validation loop.

Loop structure

  1. Warm up compilation on a few selected schedule-transition steps
  2. Reset model and optimizer so warmup does not count as training progress
  3. For each step, update schedule settings
  4. Periodically run validation
  5. For each grad accumulation microstep: fetch batch, sparse-index bookkeeping, forward, backward
  6. Step the hybrid optimizer
  7. Track timing for benchmark comparison

        model(inputs, targets, cum_seqlens, bigram_inputs, training_manager.get_forward_args()).mean()

        training_manager.sparse_index_update(step, bigram_cpu)
        loss = model(inputs, targets, cum_seqlens, bigram_inputs, training_manager.get_forward_args()).sum() * grad_scale
        training_manager.sparse_index_share(step)
        loss.backward()
    training_manager.step_optimizers(step)

model.load_state_dict(initial_state["model"])
training_manager.reset(initial_state["optimizer"])

    training_manager.advance_schedule(step)
    # validation branch
    # training branch
    for idx in range(grad_accum_steps):
        inputs, targets, cum_seqlens, bigram_inputs, bigram_cpu = train_loader.send(training_manager.train_loader_send_args)
        loss = model(...).sum() * grad_scale
        loss.backward()
    training_manager.step_optimizers(step)
A key benchmark detail: the script intentionally warms up kernels first, then restores the initial model/optimizer state so compilation does not count as training progress.

7) Triton / performance layer

Much of the speed comes from custom low-level kernels: symmetric matmuls, fused MLP work, fused loss, transpose helpers, and FP8-oriented paths.

What lives in triton_kernels.py

  • XXT and XTX for symmetric matrix multiplies
  • kernels used by Polar Express / Muon-style orthogonalization
  • fused linear + ReLU² kernels
  • fused soft-capped cross-entropy
  • transpose copy / transpose add helpers

Mental model summary

If you need a simple way to explain this codebase to someone else, use these three sentences.

1. It is a pipeline, not just a model file

The repo is built around a full training system: launch, distributed setup, data packing, forward pass, fused loss, optimizer stepping, validation, and logging.

2. The model has several side channels

The transformer core is augmented with bigram embeddings, value embeddings, paired-head attention, skip gating, smear, and backout behavior.

3. Speed comes from systems engineering

The biggest gains come from kernel fusion, communication overlap, sharding, FlashAttention-3 varlen execution, FP8/custom ops, and schedule tuning.

Best way to read the repo: start with run.sh, then skim train_gpt.py in this order — distributed setup → data loader → model forward → TrainingManager → main loop → Triton kernels.
